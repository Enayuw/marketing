# 简历职责详述 — Marketing 营销平台

## 项目背景

面向多家金融/互联网甲方的 **营销数据运营中台**：承接人群上传、数据清洗、批量跑分、转化回传，并通过 MQ、SFTP、gRPC 对接电销、决策、客服等下游。代码为 **Java 17 + Spring Boot 2.7** 多模块单体仓库，按应用拆分部署（API、MQ 消费、跑分、校验、文件桥接、甲方定制等）。

### 职责 1：客户侧数据接入与异步落库（#1、#2、#7–#12）

**业务背景**：甲方通过 HTTP 批量上传预营销人群与转化数据，要求高峰削峰、幂等与多队列隔离。

**业务逻辑**：`MarketingUserPreController` 接收 `apiCode`+加密 `jsonData` → 发 RocketMQ → `MarketingPreUserReceiveConsumer` 等消费写入 `marketing_sync_info`；转化走独立 Topic（含应急、小流量队列）。

**关键技术点**：RocketMQ 5.x 多 Tag/Topic 隔离、`BaseMqMessageListener`、敏感字段 `BrCipherJsonUtils`、`RuntimeDataContext` 埋点、幂等表。

**面试一句话**：用 MQ 把同步 HTTP 改成异步削峰，并按主/应急/小流量拆 Topic，保证上传高峰不拖垮入库。

---

### 职责 2：跑分任务调度与可控中断（#3–#6）

**业务背景**：上传数据需按客户规则批量评分，运营需能暂停/恢复跑分。

**业务逻辑**：`BuildTaskJob` 生成 `marketing_task` → `TaskScoreStartJob` 调度 `TaskScoreServiceImpl` 执行 → `ResultCheckJob` 校验产出；`TaskActionJob` / `ObservedScoreThreadServiceImpl` 支持人工暂停与告警。

**关键技术点**：Elastic-Job 分片调度、任务状态机、告警 `AlarmApiClient`、与 Customer/RuleOfScore 配置联动。

**面试一句话**：跑分是 Elastic-Job 驱动的有状态批处理，通过观测服务 + 告警实现可中断、可恢复的长时间任务。

---

### 职责 3：数据清洗引擎与原始数据治理（#17–#19）

**业务背景**：定制上传、SFTP 文件数据格式不一，需可配置规则清洗后再进入上传主线。

**业务逻辑**：`marketing_customer_original_data` 分页拉取 → 线程池按 `MarketingDataCleanGeneralRuleConfig` 执行 `dataCleanHandler` → 写回 `marketing_sync_info` 并更新 `clean_status`。

**关键技术点**：MyBatis 分页、线程池批量、Aviator/规则配置、试跑与正式 `apiCode` 隔离、`TrackingService` 流向埋点。

**面试一句话**：清洗是「原始表 + 可配置规则 + 线程池批处理」，把非标准入参标准化后再走统一上传链路。

---

### 职责 4：SFTP 文件链路与结果回传（#20–#25、#24）

**业务背景**：部分甲方只提供文件；跑分结果需合并为大文件回传客户 FTP。

**业务逻辑**：`GetFromSftpJob`/`SftpToDbBy*` 入库 → 跑分/转化 → `UpdateFileJob` + `MarketingPushTaskFileMergeConsumer` 分片合并 → `PutToSftpJob` 外推。

**关键技术点**：SFTP、分片合并 MQ、文件任务表、MinIO 部分任务（`FileUploadTaskMiNiOJob`）。

**面试一句话**：文件链路是 SFTP 双向 + MQ 驱动合并，解决大文件分片与回传一致性问题。

---

### 职责 5：对内运营平台与规则配置（#13–#16、#37–#41）

**业务背景**：运营需配置客户、跑分规则、推送过滤、同步报表，无需改代码发版。

**业务逻辑**：`marketing-inner-api` 提供 Customer、RuleOfScore、PushRuleFilter、SyncConfig、DataClean、权限等 REST；配置驱动下游 Job/MQ。

**关键技术点**：Spring MVC、Swagger springdoc、RBAC（`MarketingAuthController` 等）、配置与运行时解耦。

**面试一句话**：对内 API 是「配置中心」，用数据库规则驱动 Elastic-Job 和 MQ 消费者行为。

---

### 职责 6：下游 DaaS 推送与规则调度（#27–#32）

**业务背景**：评分/转化结果需推电销、决策、客服；部分客户按周期自动推决策。

**业务逻辑**：`MarketingPushDaasTransferConsumer` 等消费 `MarketingOutsideInterfaceConstants`；`marketing-rule-scheduler` 的 `ToPolicyByRuleJob`、`ValidPeriodResendJob` 做周期推送。

**关键技术点**：RocketMQ 推外部、规则调度、推送状态回查 `CustomerPushStatusQueryJob`。

**面试一句话**：出站链路用统一对外 Topic + 规则调度模块，把「何时推、推给谁」从业务代码里抽成配置。

---

### 职责 7：甲方定制集成（携程/同程/58/滴滴/AI 等）（#43–#60）

**业务背景**：头部客户有独立撞库、报表、CPA、AI 预用户等协议，不能挤在通用 API 里。

**业务逻辑**：独立模块 `marketing-xc-*`、`marketing-data-monkey`、`marketing-data-relay-service`、`marketing-ai-*`；Elastic-Job + 专用 MQ Consumer 实现撞库、补偿、报表。

**关键技术点**：多 Topic 报表消费、延迟队列、专线 Job 开关守护、定制 Controller 无签名/有签名两套。

**面试一句话**：定制集成采用「专线应用 + 共用 cs 域模型」，避免通用链路被甲方特殊协议污染。

---

### 职责 8：可观测、重试与稳定性（#64–#67）

**业务背景**：长链路失败需自动重试、过期监控、对账。

**业务逻辑**：`RetryCommonServiceJob`、`MonitoringExpirationAlarmJob`、`AutoCheckResultJob`；MQ Delay 队列处理合并失败等。

**关键技术点**：Elastic-Job 重试、钉钉/邮件告警、Prometheus `PrometheusTimeMethod`。

**面试一句话**：稳定性靠 Job 重试 + 延迟 MQ + 告警三板斧，而不是在业务里散落 try-catch。
